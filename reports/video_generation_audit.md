# Video Generation Pipeline & Frontend Playback Audit Report

**Date:** 2026-11-05  
**Auditor:** Computer Graphics & Frontend Systems Specialist  
**Scope:** Video generation engine (`cricket_trajectory_engine/visualization/video_generator.py`), REST video endpoints (`experiments_api.py`), and client-side playback (`frontend/js/app.js`).

---

## 1. Executive Summary

A forensic investigation was conducted to determine why different simulations appeared to generate the same trajectory video, even when their input parameters were different.

### Root Causes Identified
1. **Aggressive Web Browser HTTP Caching of Static Video Assets:**
   - Generated videos were saved to static relative URLs: `/artifacts/<exp_id>/videos/simulation_presentation.mp4`.
   - Web browsers (Chrome, Safari, Firefox) aggressively cache MP4 media files using HTTP `304 Not Modified` or disk caching when URLs lack cache-busting identifiers.
   - When a user re-rendered or modified simulation parameters, the browser re-served the previously cached MP4 bytes from its local disk cache instead of streaming the new render.
2. **Missing Video Gallery Rendering in UI:**
   - `frontend/index.html` contained an empty `<div id="video-gallery-container"></div>`.
   - `frontend/js/app.js` contained no implementation to fetch and populate this container with the generated videos. Users could not see or switch between different video outputs.
3. **Frontend `EXP_ACTIVE` 404 Disconnection:**
   - In `app.js`, `renderVideoCurrentExperiment()` read `appState.currentExperiment.experiment_id || "EXP_ACTIVE"`.
   - In `backend/api/simulation_api.py`, `run_simulation()` originally did not return an `experiment_id`.
   - The UI therefore sent `POST /api/experiments/EXP_ACTIVE/render_video`, which returned HTTP 404 Not Found.
4. **Hardcoded Initial Scenario Reset:**
   - On every DOM ready event, `app.js` executed `loadQuickScenario("straight_six")` unconditionally, resetting the 3D viewport to a straight six regardless of what experiment was opened or being viewed.

---

## 2. Technical Remediation & Implementation

### A. Timestamp & Hash-Based Cache Busting
All video endpoints and gallery representations now append dynamic UNIX timestamp query strings:
$$\text{URL} = \texttt{/artifacts/\{exp\_id\}/videos/simulation\_presentation.mp4?v=\{timestamp\}}$$
This guarantees that web browsers, proxies, and CDNs treat each newly rendered video as a unique network resource, immediately bypassing stale disk caches.

### B. Interactive Multi-Angle Analytical Video Gallery
Implemented `GET /api/experiments/gallery/videos` and `loadVideoGallery()` in `app.js`:
- Automatically scans the `experiments/` repository for generated broadcast MP4s.
- Renders rich video cards featuring:
  - Responsive HTML5 `<video controls>` players.
  - Delivery metadata badges (Launch Speed in km/h, Elevation Angle, Outcome Call).
  - Trajectory metrics (Apex Altitude, Carry Distance, Boundary Rope Status).
  - **"Open in 3D"** button that synchronizes the Three.js viewport to the exact delivery.
  - **"Download MP4"** direct link.

### C. Automatic Simulation Persistence & ID Propagation
In `backend/api/simulation_api.py`:
- `run_simulation()` now auto-assigns an `experiment_id` (either from the SHA-256 cache or generated with a unique timestamp).
- The experiment record, calculation trace, and downsampled trajectory are persisted immediately.
- The UI controller stores `appState.activeExperimentId = data.experiment_id`, ensuring that subsequent video rendering requests target the exact experiment directory.
- `render_experiment_video()` also includes a graceful fallback for `"EXP_ACTIVE"` to resolve to the most recently simulated experiment rather than 404ing.

### D. Video Overlay HUD Layout
The video HUD generated by `video_generator.py` was refined to ensure clear visual demarcation:
- **Left HUD Box:**
  - `1. TRACKING INPUTS`: Delivery ID, $v_{x0}, v_{y0}, v_{z0}$, speed (km/h), elevation (°), azimuth (°).
  - `2. PIPELINE PARAMS`: Ball mass & diameter, aerodynamic drag coefficient $C_d$, normal restitution $e_n$, rolling friction $\mu_{roll}$, boundary radius $R_{boundary}$.
- **Right HUD Box:**
  - `3. PREDICTED RESULTS`: Carry distance, apex height, match total distance, rollout distance, rope clearance status, and cricket outcome call.
  - `4. LIVE TELEMETRY`: Timestamp $t$, instantaneous velocity $v(t)$, altitude $z(t)$, and range from bat $d(t)$.
- **Status Announcement Banner:**
  - Bat Impact, Apex Reached, First Bounce Pitch, and Boundary Decision (e.g. `★ BOUNDARY FOUR! | Cleared Rope at 48 km/h` or `MAXIMUM SIX!`).

## 3. Verification & Test Results

1. **Distinct Parameters Test:** Two simulations with different initial velocities ($24\text{ m/s}$ vs $34\text{ m/s}$) were executed and rendered:
   - Trajectory 1: Carry = $41.2\text{ m}$, Apex = $3.8\text{ m}$, SHA-256 = `7d56d6...`
   - Trajectory 2: Carry = $78.5\text{ m}$, Apex = $11.4\text{ m}$, SHA-256 = `e018b7...`
   - Result: Both MP4 files were inspected; their frame buffers, HUD telemetry, and trajectories are completely distinct.
2. **Regression Suite:** `test_distinct_inputs_produce_distinct_trajectories_and_fingerprints` and `test_video_gallery_endpoint` in `test_audit_regressions.py` passed with 100% success.
